> I'm the schema agent. My job for this session is to lay the foundation for the `contracts` module — the Drizzle table, Zod schemas, and service interface. I generate stubs only. No method bodies, no components. The code agent fills those in later.

>
> ---
>
> **The data model from SPEC.md section 6.1.6 gives us these fields:**
>
> | Field | Type | Notes |
> |---|---|---|
> | `id` | uuid | System-generated |
> | `org_id` | uuid | Mandatory — org-with-units scoping |
> | `org_unit_id` | uuid | Mandatory — branch scoping (org-with-units pattern) |
> | `start_date` | date | User input |
> | `account_manager_id` | uuid | User input |
> | `contract_type` | enum | standard, premium, enterprise |
> | `status` | enum | draft, pending, active, expired, cancelled |
> | `commission_rate` | decimal | Sensitive/PII — Finance-only |
> | `created_at` | timestamp | System-generated |
> | `updated_at` | timestamp | System-generated |
>
> **Key design decisions I'm about to make — tell me if any of these are wrong:**
>
> 1. **Two org columns, not one.** The SPEC says `org-with-units` — that means every contract belongs to a branch (`org_unit_id`) inside a region (`org_id`). Canon Section 3: every query filters by `orgId` at minimum, and typically by `orgUnitId` when the user belongs to a branch.
>
> 2. **`commission_rate` excluded from all Zod schemas.** Canon Section 5 rule: never include a Sensitive/PII field in a create or update schema. Finance sets this through a separate, permission-gated flow (future story). If we included it now, any caller with `contracts:create` could set it, which would bypass the Finance review AC-011 is designed to enforce.
>
> 3. **`createDraftContractSchema` makes all fields optional.** AC-010 says "allow saving as Draft without triggering required-field validation." The Zod schema enforces this by being fully optional — the service layer still validates types and ranges, but won't reject a partially-filled draft. The full `createContractSchema` (for non-draft saves) keeps the fields required.
>
> 4. **`status` excluded from all schemas.** The user never sets status directly. The service sets it to `'draft'` on creation, and only specific service methods (which we'll add in later stories) transition it. User-controlled status would be a security issue.
>
> 5. **Past-date rejection in `createContractSchema` via a Zod refinement**, not a database constraint. Database constraints cause cryptic errors. Zod refinements produce the inline error message the form can display to the user (AC-003).
>
> 6. **Service method signatures use `CallerContext`, not loose strings.** Canon Section 7: every service method that writes receives `ctx: CallerContext` — never `orgId: string, userId: string`. The context carries the full auth picture (org, unit, user, permissions) in one typed object.
>

> - `db/schema/index.ts` — updated to export contracts
> - `lib/auth/permissions.ts` — updated to register `contracts.create`

>
> ```
> 1. requirePermission(ctx, PERMISSIONS.contracts.create)
>    → Throws if the caller lacks the permission
>    → Canon Section 8: write methods always check permission before touching DB
>
> 2. Parse with createContractSchema
>    → Returns { error } on validation failure
>    → Keeps service-layer errors as data, not exceptions
>
> 3. db.insert(contracts).values({
>      ...parsed,
>      orgId: ctx.orgId,           ← from CallerContext, never from user input
>      orgUnitId: ctx.orgUnitId,   ← same
>      status: 'draft',            ← hardcoded, not from input
>   }).returning()
>
> 4. audit.record({ action: 'contract.created', resourceId, ctx })
>    → Canon Section 9: every write calls audit
>
> 5. logger.info({ contractId, orgId }, 'contract created')
>    → Canon Section 10: every write logs
>
> 6. return { data: contract }
> ```
>
> Notice that `orgId` and `orgUnitId` come from `ctx`, not from `data`. Even if a caller somehow passed an `orgId` in the request body, it would be ignored — the context's org is the truth. This is how the org isolation tests pass: a caller from `orgB` can only ever create records with `orgB`'s IDs.

## What this session demonstrates

**Teaching in action:** The schema agent explained why `commission_rate` is excluded from schemas, why `status` is excluded, why `orgId` comes from `ctx` not from user input. By Phase 7, the developer has been walked through the security model three separate times in different contexts. If they open the code agent's output and see `orgId: ctx.orgId`, they already understand why.

**Bug caught at Phase 6:** The Zod refinement bug (comparing against `new Date()` with time component instead of midnight) was caught during test writing, not during implementation. This is exactly the value of Phase 6 — the test agent's job is to write down what should happen precisely enough that ambiguity surfaces. "Past start date is rejected" sounds clear until you write a test for "today" and realize today is ambiguous.

**Phase 7's discipline:** The code agent never modified tests. It fixed a real bug (the Zod refinement) but did so by fixing the schema, not by changing the test to expect the broken behavior. The test was the truth; the code was wrong.

**One continuous session, four phases:** The accumulated context — the commission_rate exclusion decision, the past-date bug fix, the CallerContext explanation — didn't need to be re-established in each phase. The compacted summaries (30–50 tokens each) carried the key decisions forward. Total session cost was substantially lower than four separate sessions would have been.

---

## What changes between US-001 and US-002

US-002 (audit log) follows the same four-phase pattern with two meaningful differences:

1. **Phase 5 is smaller.** No new table — the audit table exists. Phase 5 only updates the service interface to annotate which methods will call `audit.record()`.

2. **Phase 7 already exists in Phase 5 of US-001.** The `contractService.create()` already calls `audit.record()` — it was built into US-001's implementation following the canon. US-002's Phase 7 verifies it works as expected, possibly tuning the audit record fields. This is the spec dependency (US-002 depends on US-001) paying off.
